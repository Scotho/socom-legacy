## 2. W2-B-01 — make the service-to-match handoff concrete

This is an implementation breakdown of the already-authorized **SVC-07a**, not discovery of a missing entire lobby. PORT roadmap `06-online-services.md:300–319` explicitly calls for game registration, identity, readiness, and launch before the separately deferred results bridge.

The disconnected pieces are now precise:

* PORT `central/src/main.ts:55–76` mounts server texts and clan-invitation handlers when `DATA_DIR` is present. The production-source census finds definitions of `accountHandler` and `lobbyHandler`, but no production call constructing `RoomService` or mounting those two handlers. This is a bounded search over `packages/**/src/*.ts`, reinforced by the actual main entry point, not an assertion about every possible external entry point.
* PORT `central/src/lobby.ts:408–434` creates a distinct `mediusWorldId`, host account, per-game fields, passwords, members, and pending status. `joinGame:442–458` checks the selected world's existence, ban, password, total capacity, and spectator capacity. `lobbyHttp.ts:14–21,51,129–160` requires a resolver that derives an account from a live server-side session; request bodies do not supply that authority.
* PORT `match/src/server.ts:229–247,344–394` instead chooses a room by uppercase map plus classic/respawn rules and accepts the anonymous hello directly. `viewer/src/net/protocol.ts:315–350` has no service world/admission identifier. Two separately created games on MP51 cannot safely be connected by simply passing their map to that existing method: they would address the same room.
* PORT `accounts.ts:247–259` returns a random login ticket and permits it to be claimed once. A replacement socket cannot simply call `claimTicket` again with the already claimed ticket. The page token in `viewer/src/net/session.ts` is a separate browser reconnect identity, not an authenticated account.
* PORT `lobby.ts:546–571,592–599` ends hosted games on `leaveGame`/`logoff`, and `unseat` ends a game when its host or final member leaves. PORT `server.ts:320–323` already avoids processing a replaced socket's close as a live seat departure. Naively calling account/lobby logoff on every close would undo that protection.

**Original evidence:** `FUN_002edda0` D190492–190580 submits game creation; `FUN_002ee090` D190603–190640 keeps the returned world ID and proceeds to joining; `FUN_002eda60` D190355–190404 submits the selected game ID, join type, and applicable password; `FUN_002edba0` D190407–190487 consumes connection information. PORT-154 already traces these service request/reply contracts. The web admission protocol, ownership of sockets, replacement grace, and multi-tab policy remain browser/server design; they are not retail constants to reverse engineer.

**Proposed implementation contract:** an authenticated account session resolves a membership/admission for a particular `worldId`; a page session/replacement generation identifies a browser seat within that membership; a live room is keyed by `worldId`, with a separate map/round generation. Immutable map parses may remain cached by stem. A socket replacement transfers only the admitted seat and invalidates the older connection's authority. A genuine leave, expired reservation, failed map load, world destruction, and account logout have distinct transitions. Explicitly define which event ends the host's world and which preserves it during the existing reconnect window. Reuse existing account and lobby modules rather than introducing parallel identity stores.

**Acceptance owed:** create two worlds for the same map and rules and prove isolation of players, score, doors, charges, and bans; reject a hello for another/ended world; exercise password and watch admission before spawn; close the old socket after its replacement is active and retain the new membership; fail/cancel map loading and release the reservation; make repeated cleanup idempotent. Verify the account HTTP resolver and socket identity use the same claimed session without accepting body-supplied account identity. These are future tests, not tests run by this audit.

## 3. W2-B-02 — settings, counts, and map lifecycle must share one effective record

M1 G13–G20 already identified the rules/settings gap. This wave adds the integration shape and rejects two misleading shortcuts.

PORT `central/src/main.ts:72–73` supplies global round seconds, round count, and offered rules. `RoomOptions` at `room.ts:45–96` has no game-world settings object, friendly-fire option, equipment-limit option, playlist, or per-game seat capacities. PORT `viewer/src/net/lobby.ts` separately owns the active player's seat/queue machinery. Meanwhile `RoomService` stores the game report and counts service members. Merely rendering CREATE GAME, or allowing its JSON fields into `RoomService`, does not change the match simulation.

**Original fields, already sourced but important to keep separate:** `FUN_002f7c40` D196724–196752 writes the normalized 'D' record: byte 1 rounds, byte 2 integer minutes, byte 3 the current spectator count, byte 4 spectator slots, byte 5 equipment limitation, byte 6 sort priority, byte 7 rank bits, bytes 8–39 playlist. **Byte 3 is a count, not a spectator-enabled boolean.** `FUN_002edda0` D190520–190550 forms service MaxPlayers from player slots plus spectator slots when enabled. `FUN_002e2ce0` D184417–184437 draws players and spectators separately; game-list MAX is `min(totalMax - spectatorSlots,16)`. M1 G13 traces RulesSet and native GameState flags; game mode, respawn choice, friendly fire, and browser room rules are distinct fields.

**Count ownership issue:** PORT `lobby.ts:582–588` uses `livePlayers(worldId) ?? members.size` for total occupancy, but counts spectators from service `joinType`. PORT `joinGame:452–453` checks overall capacity plus a separate watcher cap; it does not promise that a join as Player immediately occupies a playing team slot. The live browser lobby can queue a joiner as spectator and later promote/demote it. Therefore the bridge must synchronize active role and membership, or deliberately retain separate “admitted join type” and “current seat role” counts. Passing the playing-player count alone as `livePlayers` would conflict with the retail total-count field. This is an integration requirement, not a claim that an unmounted endpoint currently exposes a live bypass.

**Proposed record:** validate one immutable effective match configuration at creation/report/launch boundaries, including map playlist and selected map index, game mode, rounds/time, friendly fire, respawn policy, playing/spectator limits, equipment limit, and settings revision. Feed both the advertised list and `Room` from it. Dynamic values such as spectator count and world status come from the live membership owner, not stale host-authored bytes. Keep passwords and account admission out of the simulation record. Preserve the owner's classic-only policy; do not enable respawn merely because a retail field exists. If respawn is later authorized, M1 G17's suppression-only restriction still applies.

**Map lifecycle:** the existing `MatchServer` room key is also the teardown unit. SVC-07a plus playlist progression must end/rebind the live simulation for the selected world's next map without merging another world's room, retaining an old room's projectiles/doors, or accepting late events for a previous generation. The all-map gameplay plan supplies objective behavior; this report supplies world ownership and reset boundaries. Native `AdvanceMPMission` (`FUN_00279490`, M1 G16) and the original match-to-lobby path (M1 G23) are covered; automatic same-map restart is the current browser flow, not proof of original map rotation semantics.

**Acceptance owed:** two worlds with different round/time/seat settings; list counts through watch, queue, promotion, demotion, replacement, and leave; staged report updates cannot silently mutate the current round; total-capacity and watcher-capacity boundary cases; map advance rejects prior-generation inputs; each mode's map metadata agrees with the effective record. Exact retail picker ranges still need data decoding/capture where M1 left them open. Do not invent ranges from the current server's guard constants.

## 4. W2-B-03 — persistent projectile state and identity

**Observed implementation contract:** PORT `Room.flying` retains live grenades/charges. Creation paths at `room.ts:1711–1712,1766–1769,1834,1866` emit one `grenade` event. `hello:578–587` sends roster, rule/count metadata and score; `snapshots:2435–2447` sends only own mover, bodies, and doors. Neither serializes `flying`. PORT `protocol.ts:533–534` carries only owner player ID, kind, position, and velocity. There is no projectile ID, lifecycle state, age, fuse clock, or current placed-charge list. `netPage.ts:914` invokes visual creation only when that event arrives. A spectator or fresh page joining later cannot reconstruct an existing mine, flying grenade, or persistent visual phase from the messages available.

**Native consumer evidence, reconciled with the newly published M2 report:** `FUN_002c1850` D163774 onward registers the 0x24-byte GrenadeState schema and callbacks; `FUN_002c1420` D163598 onward publishes position, velocity, owner u16, and monotonically advanced projectile state, deleting the network object at state 3. `FUN_002c17b0` D163753–163767 resolves the owner and creates a remote projectile through its kit. `FUN_002c16a0` D163715–163732 applies position, velocity, and state, including the all-fields callback case; `FUN_002c15e0` handles deletion. Launch registration is conditional in `FUN_003cb1a0` D320763–320779: online, a qualifying weapon/projectile branch and local-authority flags. M2 §2.4 and §4.3 now cover the schema/consumer foundation; this wave independently checked it. `FUN_0061ba10` D527450–527468 sends full owned objects to new clients, also re-read here. The new contribution is the PORT hydration/ownership mismatch, not rediscovery of that original mechanism. This establishes an original persistent-object mechanism, **not** that every throwable class has identical late-join behavior. The record does not establish a replicated fuse-age field; do not claim one.

**A second, narrower PORT mismatch is closed by code:**

| Transition | Server predicate | Existing observer predicate | Consequence where the Detonator is eligible |
|---|---|---|---|
| Same player | `Flying.owner === Player` | stored numeric owner equals event ID | Agrees |
| Takeover allocates a new player ID | `seat:817` reassigns retained `Flying.owner` to replacement Player | charge still holds old numeric ID | Server can trigger a charge whose observer copy does not match |
| Departure, then different player reuses the old ID | retained charge owner is a different Player object | numeric IDs match | Observer can trigger a departed player's charge that server refuses to trigger |

Anchors: PORT `room.ts:1715–1732,1788–1792,798–818`; `server.ts:530–533` reuses the lowest free ID; `grenade.ts:1060–1084` stores/tests numeric owners; `netPage.ts:843` handles `left` by forgetting the actor/team/votes, with no charge-owner rekey. No such charge-owner rekey API was found in `GrenadeThrower`. The predicate model (`research-wave-2026-10-04/wave-2/scratch/W2-B/contracts.json`) computes these comparisons only; it does not simulate eligibility, physics, or gameplay. **Timing qualification:** in an active classic round the replacement/new joiner is a ghost until the next round, whose reset clears charges. A meaningful current-policy reproduction is the browser waiting phase with an observer and placed charges; respawn is owner-disabled. Do not report this as a demonstrated active-classic exploit or original-game bug.

**Prior damage rule to preserve:** C1's completed report L927–939 traces `FUN_005ac670`'s friendly-fire owner lookup: it reads the owner's current team at impact; when owner lookup fails after departure, that friendly-fire gate does not apply. This is C1's source closure, not a new W2 rule. Integrating stable projectile identity must keep detonation authority, damage eligibility and score attribution distinct; a retained owner object or throw-time team must not silently replace the sourced impact-time lookup. The native projectile-creation/late-join owner-failure cases remain separately bounded.

**Proposed work:** introduce stable projectile identity scoped to the map/round generation, separate from the recyclable actor wire ID. Serialize current live projectile/charge state for joins and replacements; retain the original kind and applicable motion/rest/facing state and enough phase timing for browser rendering. A continuing smoke/effect phase needs its own retained effect record if it outlives the projectile: `flyGrenades` removes entries when state becomes `removed` (`room.ts:1935`), so serializing the current `flying` array alone does not establish complete effect restoration. Link credit/ownership to the room's stable seat/owner policy, and expose ownership transfer or ownerless state to observers where needed. Prefer authoritative detonation/removal by projectile ID over replaying a “Detonator” command against divergent local lists. Reconcile optimistic local throws against server acceptance without replaying spent inventory or historical blast audio.

**Acceptance owed:** join during a flying grenade, after a claymore/PMN/C4 is placed, and during a continuing smoke phase; takeover and ID reuse with a witness; leave with charges retained; ensure late observers see existing state without receiving a historical kill/blast; clear exactly once on map/round reset; keep damage/scoring authoritative and once-only. Include C1's departed-owner friendly-fire case without conflating it with score credit or charge control. Source follow-up: enumerate each throwable's native registration predicate and create/apply ordering. Runtime gate: two original consoles joining at controlled projectile phases, including owner departure; capture creation/rehydration owner-lookup failure behavior and validate C1's impact-time rule. This extends M2/C1, not a new claim to have measured their packets or gameplay.

## 5. W2-B-04 — restore current round and result state

PORT `Room.state` distinguishes waiting, play, decided/expired and over intervals, but its welcome has only round number, maximum rounds, ghost/wait/countdown metadata (`room.ts:578–583`). `scoreEvent:2399–2406` has rows, wins, spectator names and `timeLeft`, which is null outside play/decided (`2394–2396`). The snapshot schema has no match phase. Result content is emitted once by `roundOver` (`room.ts:2338`), and PORT `netPage.ts:948–951` starts its local result-screen clock at receipt. Welcome `805–840` and score `953–957` cannot reconstruct that screen list, winner, match-over flag, or elapsed screen time. Thus a spectator joining halfway through a result interval lacks the current panel and its remaining duration. A client that stayed connected receives the event; the problem is state restoration, not loss of WebSocket reliability.

**Original comparison:** M2 already inventories GameState. Fresh consumer reading here verifies `FUN_002a9ee0` D150679 onward publishes clock/control fields, and `FUN_002c0850` D163312–163353 applies clock length, start and packed state, including `param_3 == -1` full application; changing the game-state byte calls `FUN_002a7490`/`FUN_002c5360`. This supports restoring current control state. It does not by itself establish which exact original result panel a late joiner sees; that remains an explicit capture gate. Existing C1-D already supplies the result screen data and timing; do not re-invent it.

**Proposed work:** a coherent `RoomView`/match-state record in welcome and phase updates: world/map/round generation, current phase, phase start/deadline in server time, round/match counters, current result data and any screen sequence index. Derive the visible screen from elapsed authoritative time. Keep transient announcements separate: hydration must not award score again or replay every past elimination line/music cue. Include the owner's waiting/countdown behavior as an explicit branch, not a fabricated original phase.

**Acceptance owed:** join/reconnect at every phase boundary and midway through every result screen, including the final result; compare old observer and joiner panel and remaining time; reorder replacement-close relative to hydration; cross a new-round edge while joining without briefly showing the preceding result. Original-runtime gate is narrowly the late-join screen behavior, not another broad packet census.

## 6. W2-B-05 — hydrate corpse age and pose

PORT `room.ts:2131–2156` saves `victim.diedAt` but transmits the selected death clip only in the one-time `kill` event. `BodyState` (`protocol.ts:188–222`) supplies Alive plus ordinary motion/action fields, with no death time or selected death clip. `RemotePlayers.add` (`remotePlayers.ts:429`) begins with `deadFor:0` and a clip only if an earlier kill was queued locally. `frame:338–351` adds local frame time while dead, shows the body until `BODY_FADE_S`, and overrides the pose only if a death clip is known. A new spectator first seeing a body after its older observers have faded it restarts visibility for roughly the local fade period and cannot recover its selected death pose. The source/predicate model uses a 20-second-old body with a 10-second fade; it is not a rendered capture.

**Native comparison, bounded:** M2 `SealState` creation is `FUN_002bf070`, which calls full-state `FUN_002be150` after constructing the remote actor (D162596–162602). The reader's controller-state branch (D162386–162395) can set health to zero and enter actor state 8 from the replicated flag. Native health fields are also applied (D162325–162346). This is concrete state-consumer evidence, but the exact late-join native death pose, fade age and ghost distinction are not closed by those calls. This report does not claim a retail death-time field has been found.

**Proposed work:** retain selected death representation, death tick and lifecycle generation on the server; hydrate a corpse with elapsed age, avoiding a new killfeed entry or score event. Distinguish an actual corpse from an unspawned ghost so a ghost's absent live body is not treated as a fresh corpse. Keep falling/blast corpse motion compatible with existing motion state; a universal frozen death clip would lose those paths. If original capture instead shows a different late-join presentation, document that as the parity rule rather than silently assuming the proposal is original behavior.

**Acceptance owed:** a new observer at death+0.5s, +5s and beyond the fade; chosen head/body/prone clip, fall/blast corpse, and ghost who has never spawned; a previously seen ID reused or respawned; ensure hydration does not restart audio/killfeed. W2-A owns dropped kit/pickup state; that state will need independent persistence even if the corpse model is no longer visible.

## 7. W2-B-06 — close the game-list sort byte

M1 G31 left `mp_game_sort_order` meaning unread. Its downstream consumer is now traced:

1. `FUN_002f7c40` D196734–196735 writes the valve to 'D' byte 6. `FUN_002e1d50`/`FUN_002e1e10` store normalized 'D' data at list-entry +0x19a (prior PORT-154), so byte 6 is +0x1a0.
2. Game-list draw `FUN_002e2ce0` calls `FUN_002e4530` at D184407; that calls the sorting routine at D185372.
3. Small-list `FUN_002e5d90` D186117–186141 compares the **unsigned byte ascending**, then `FUN_00198b80` on the **full name at +0x4c** when equal. Larger-list `FUN_002e4a90` D185623–185646 uses the same comparator. ELF instructions at `0x2e5e2c/30` are `lbu ...0x1a0`; `0x2e5e40` calls `0x198b80`; `0x2e5e50` uses the unsigned less-than comparison. `FUN_00198b80` is the caseless byte-string comparator; this is not a locale-aware browser sort.
4. Named creation path `FUN_002f9410` D197758–197770 sets persistent to 0 and this priority to **0x7f** before its create transition. This specific path is not proof that every built-in/persistent game uses 127.

The now-completed C8 report L426–439 already sources the `$~<room>` suffix and this ordinary-create persistent=0/priority=127 initialization. Credit those as supporting prior coverage. The new closure here is the priority-byte comparator and caseless **full internal name** tie-break. C1's round-result score/kills/name ordering at L1931–1954 concerns a different list and does not substitute for this game-browser comparator.

PORT `lobby.ts:715–725` renders game columns but lacks a corresponding game-list ordered-row helper. Its `roomListRows:745–753` sorts **briefing rooms** by another field and must not be reused as a game's rule. Service `gameList` enumerates by world ID for pagination (`:383`); changing that service wire order is unnecessary to reproduce the client-side draw order. Add the client-side game-list ordering after receiving the listed entries, before rendering/filtering as the actual page requires. Compare full internal names, including any `$~<room>` suffix, before applying `drawnName`; the native sort points to +0x4c, while visible truncation is a separate text consumer.

**Validation:** priorities 0/127/255, equal priority mixed case, names sharing the drawn prefix but differing after `$~`, and more than 20 entries (both retail algorithm branches share one comparison rule). Probe outputs verify selected machine instructions; root independently checked `FUN_00198b80`'s character-class lowercase conversion and the tie-break reading. A console list capture remains the visual parity check. New source grade: source reading, not runtime proven.

## 8. W2-B-07 — bound `mp_persistent` instead of inventing a gameplay meaning

The creation-failure behavior was already documented in PORT-154. Fresh verification: `FUN_002ee090` D190603–190635 reads `mp_persistent` (ELF string `0x3f4948`). With it off, failure uses the normal name-exists/join-failure paths. With it on, the function constructs a FindWorldByName request of type 0, handled by `FUN_002ee210` D190656–190664. This is a named-game service/lobby behavior.

The new retail UI probe (`research-wave-2026-10-04/wave-2/scratch/W2-B/ui-consumers.json`) decodes four matching animation sequences from `RUN/UIZANIM.ZAR`, SHA-256 `375b3cf88cb4b412bf509339396804ecb4b9d6f987092e714dfac4dc5999495f`:

* `dlgCreateGame.rdr / GameNameAct / NA`, decoded op 2 sets persistent=1.
* `dlgMPBriefingRoom.rdr / OnBriefingRoomstart / NA`, op 15 resets it to 0 in the `NoExitState != 1` branch.
* `dlgLANBriefingRoom.rdr / OnBriefingRoomstart / NA`, op 21 has the corresponding reset.
* `dlgGameLobby.rdr / Session_master_migration / watch_for_switch_to_master`, op 9 conditionally enables and activates the Lock control when persistent==0, followed by `OnStartGameLock` outside that condition.

The JSON uses decoded-op indices and sequence-block-relative offsets. It does **not** equate a filtered decoded-op index with a raw command offset. This matters because alignment operations can be removed by decoders.

Native GameState also propagates the persistent bit (M1 G31, writer D150770–150771; reader `FUN_002c0850` D163387–163401). The named creation command `FUN_002f9410` sets it back to 0 on its ordinary create path. Together these consumers narrow the field to real UI/service control. They do not establish “preserve bridges/bomb/score over rounds,” “never destroy a hostless world,” or a server uptime policy. Do not map the word directly onto any of those meanings.

C8 L426–439 now supplies prior coverage for that named-create default; C1 L466–474 still leaves the valve's broader meaning partial. This section extends those results with verified fallback/FindWorldByName and decoded lock-control consumers. The fallback itself was already documented in PORT-154; the new contribution is connecting and bounding these consumers, not claiming a newly discovered persistence feature.

**Proposed work:** carry the field only where the original UI/service flow requires it; reproduce the lock-control branch if that lobby path is included. Keep the existing fallback behavior categorized as covered. **Owed:** trace all named/persistent game entry paths and relevant GameLock consumers before implementing a broader lifecycle policy; capture the lobby master migration/lock presentation if parity for that branch is required. No broad persistent-world implementation is justified by this label alone.
