## 2. The widget TYPE tallies (PLAT-05)

### 2.1 The rule

Each `TYPE` value of each READERC `dlg*` layout is counted by where it stands (`typeSites`): **widget** -- a record
under `OBJECTS` or `CONTROLS` (what `parseUiLayout` returns as `objects` and `controls`); **subordinate** -- a widget
inside another (`SUBORDINATES`: a `RADIOSTRIP`'s `CHECKBOX`es); **element** -- a `MAPCONTROL`'s `ELEMENTS` (no `NAME`);
**background** -- `BACKGROUND`'s `TYPE`; **uivar** -- a `UIVAR`'s `TYPE`, its longevity (`PERMANENT`). A record with its
`TYPE` key twice counts once.

### 2.3 What the readers met (worked around in the tool; the readers are PLAT-05's and PLAT-27's)

- Fourteen layouts (twelve `dlg_Brief_*`, `dlg_CharUnlock`, `dlg_WeapUnlock`) end with loose tokens (`:end of file`,
  `:end of Def's`) beside their `SCREENS` record, so `parseUiLayout(parseRdr(...))` throws "dialog has no SCREENS"

  a strict key/value walk does not (`dialogInventory.ts` reads pairs as `rdrGet` does).
- The three-token `NAME` and the doubled `TYPE` keys above.
- Some layouts spell `LIBRARY`, not `LIBRARIES` (`dlgIntroScreen`, `dlgExitState`): `parseUiLayout` returns no library
  for them.

## 3. The flow graph and the classification

### 3.1 How an edge is read

`buildGraph` (`tools/dialogInventory.ts`), over READERC's 103 dialogs and the three archives' named sets. A dialog's
sets are its `SCRIPT_LIBRARY` names, each looked up first in the archive holding the dialog's own set, then UIZANIM,
EXTZANIM, MPZANIM (`SET_RESOLUTION_READING`, §10). For each binding of the layout (`EVENT` / `BUTTON` / `TRIGGER` +
`ANIMATION` + `ARGUMENT`, at screen level or on a control), the animation is found in those sets and its bound-function
commands are collected, following `CALL_ANIMATION` (a name no set defines is a no-op, research 95 §1.4); a command's
argument `INPUT_STRING` is the binding's `ARGUMENT` (`UIanim.rdr`'s `switch_menu`, `goto_menu`, `goto_menu_silent`).
An argument that is a dialog name (`dlg...`, with or without `.rdr`), a movie (`.pss`) or one of the switch handler's
states (`REBOOT`, `LOAD_SCREEN`, `POP_TO_MENU_STATE`, `MENU_SCREEN`, `SHUTDOWN`: the strings `FUN_00365a00` compares
with, 0x3f8c38-0x3f8c78, D:L262375-262460) is an edge. Also edges: what the dialog's own set names outside a binding
(`script`), and the layout's own strings (`layout`: a `BACKGROUND` movie). An edge is **own** when the naming command is
in the dialog's own set or layout (or takes the layout's argument), **library** when it is in a library set.

**Result** (`npx tsx tools/dump-dialogs.ts`, "edges"): 1,023 edges (575 own) -- 932 to dialogs, 27 to movies, 64 to
states (REBOOT 48, LOAD_SCREEN 15, SHUTDOWN 1) -- and 68 library-set edges no dialog's binding reaches. The pin holds
each as `from -> to [via]`.

**What the graph does not know.** A script's `IF` on a valve is not evaluated: `check_then_save_and_leave` names
`dlgMenu` and `dlgAlbaniaCinematic`, and goes to one by `ComeFromMission`-style state. An edge is "can name", not
"goes".

### 3.4 The classification

`classify`: (1) **boot** -- reached from the start dialog by own edges without passing `dlgMenu`; **main menu** --
`dlgMenu`. (2) Each `dlgMenu` branch -- online (`multiplayer_button`, `LAN_button`), campaign (`new_game_button`,
`load_game_button`, `SavedGames`), extras, options, in that order -- walked breadth-first by own edges from what its
CROSS switches to, never into `dlgMenu` or a boot dialog; what the online branch reaches is **online**, anything else
takes the branch that reaches it in the fewest switches (a tie: the earlier branch). (3) The classes then spread one
switch at a time along every edge, library edges included, to what (2) left. (4) **code** -- a dialog left that the
ELF names (§3.5), and what only such dialogs reach. Online goes first because the campaign's armory reaches the lobby
only through a TRIANGLE that returns to whichever screen called it (`dlg_equipment_main`'s
`returnto_menu_with_valve` -> `dlgGameLobby`).
